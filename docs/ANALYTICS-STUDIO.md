# Analytics workspace

The Analytics workspace has three entry points: Reports, Data sources and Prepare data. Existing dashboard URLs and saved definitions are retained.

- Reports can be searched by name or description, sorted by name or most recently updated, and viewed as cards or a table. Create report opens a blank report. Card previews identify the saved visual types; they do not invent sample figures.
- Data sources separates connected sources, connector selection and load history. Connected file sources expose their field names, original headings and types. CSV and Excel connector choices filter the available server-folder files; existing preview, type mapping, loading and nightly refresh flows are reused. Books/CRM and report-email collection use their existing services.
- Microsoft SQL Server, PostgreSQL and MySQL connectors (decisions 602-605) follow the Power BI and Looker Studio flow: choose the database type, enter the server, port (or SQL Server instance), database, user, password and encryption, test the connection, choose a table or view or write one SELECT query, preview the columns and first rows, confirm each column's type, then load into the organisation's own DuckDB copy. Database sources reload nightly and on demand, appear in Load history like files, and can be edited (the table name stays). Connections are listed per database type, only for admins and owners; a connection used by a source can't be removed.
- The Google Analytics connector (decisions 606-609) signs in with Google through the organisation's Google app, lists the GA4 properties the account can see, and loads five daily tables (`google_analytics_daily`, `_traffic`, `_pages`, `_countries`, `_devices`) with Refresh now, nightly reloads, load history and Disconnect. Connected, it appears in Connected sources too. Its help lists what an admin enables in Google Cloud, and that Google ends sign-ins after 7 days while the app is in Testing. A Website report template uses its tables.
- The chart editor places a searchable field catalogue beside a live preview and a properties panel. Choose a visual, source, dimensions, measures, filters and width, then add it to the report or apply changes. Saving is disabled while a preview is pending or invalid. Report-level save/view and delete wait until the chart editor is closed, so they cannot silently abandon an unfinished chart.
- The chart panel (#387, decisions 750-752) follows Power BI's Build / Format / Analytics panes and Looker Studio's Setup / Style tabs: **Data**, **Style** and **Interactions** tabs (`src/components/analytics/panel-tabs.tsx`, the WAI-ARIA tabs pattern). Where each Style setting comes from (the chart's own override, the report's chart type default, or the theme) is worked out by `settingSource` and reset one setting at a time by `withoutSettings` (`src/lib/analytics/editor-panels.ts`; `src/components/analytics/setting-source.tsx` draws it). Specialist chart types (`isSpecialistVisual`) and advanced settings (`usesAdvanced`) are behind a choice unless in use. Choosing tiles in edit mode offers same width, same height, share a row and line up heights (`matchSize`, `shareRow`, `alignRowHeights`, `layoutRows` in `src/lib/analytics/layout.ts`), which keep the flowing 12-column grid.
- Report themes (#376 phase 1, decisions 668-671) follow Power BI's report themes and Looker Studio's theme panel. Theme, in the report toolbar while editing, lists the six built-in themes and the organisation's own; the theme editor (colours for light and dark, fonts, text sizes, card style) shows a live preview and the colour checks, and themes import and export as JSON. The theme is scoped to the report's tiles and the chart preview; the rest of Tohyee, including pinned tiles, keeps the Tohyee look. "Set as default for <chart type> in this report" and Copy format / Paste format follow Power BI's visual defaults and format painter.
- Each chart's Format section (#376 phase 1, decisions 672-673) follows Power BI's format pane: title and card, colours (any hex per value or group, with Reset to the theme and colour warnings), data labels, legend, axes, gridlines and plot area, reference lines, trend and linear projection, tooltip, and column and line options, grouped in collapsible sections. A colour chosen on a chart is drawn as a worked-out dark version in dark mode.
- Key figures (#376 phase 1, decision 674) follow Power BI's card and new card visual: number size, colour, alignment, weight and name position; colour by rules or by the comparison; an arrow or dot; trend style and colour; and several numbers in one card.
- Tables and pivots (#376 phase 1, decision 675) have Table style and Conditional formatting sections, following Power BI: colour scales, rules or a field's colours for backgrounds and text, data bars, icons, header and band colours, gridlines, text size, column width, wrapping, totals and subtotals. Charts have Colour rules.
- More visuals (#376 phase 2, decisions 676-677): waterfall, funnel, gauge and bullet chart, following Power BI's visuals of the same names. The waterfall's running totals and total bar are worked out exactly in decimals (`waterfallSteps` in `src/lib/analytics/chart-visuals.ts`); a gauge shows one total (no grouping) and a bullet chart can show one total or one bar per group; both take an optional second value as the target. Each has its own section in the Format panel (Waterfall, Funnel, Gauge, Bullet chart) and uses the shared sections that apply to it.
- Scatter and bubble, histogram and box plot (#376 phase 2, decisions 678-679), as in Power BI's scatter chart and Excel's histogram and box and whisker charts. Bins and quartiles are worked out exactly in decimals (`histogramBins`, `boxStats` in `src/lib/analytics/chart-distributions.ts`). A tile can now have a second grouping inside the first (`breakdown` in the tile's query, returned as the `breakdown` column); for now only box plots use it ("Each box is made of"), and the server refuses it on other chart types and with last-year comparisons.
- Treemap, heat map, calendar heat map and Sankey (#376 phase 2, decision 680), as Power BI's treemap and the ECharts heat map, calendar and Sankey series. They use the second grouping (decision 679): optional for a treemap, required for a heat map ("Down the side") and a Sankey ("Flows to"); a calendar heat map is grouped by a date by day. Cell, box and flow totals are added exactly (`src/lib/analytics/chart-relationships.ts`). No external map or tile service is involved.
- Small multiples (#376 phase 2, decision 681), following Power BI's small multiples: a column, bar or line tile with a second grouping is drawn as a grid of small charts (`smallMultiples` in `src/lib/analytics/small-multiples.ts` groups the rows, fills missing groups, works out the shared scale and folds the rest into "Other" exactly). Each small chart is the tile's own chart with all its formatting.
- Pivot table (matrix) improvements (#376 phase 2, decision 682), after Power BI's matrix: nested column fields (`pivot.subColumns`, up to two inside the first column field) with column subtotals worked out by DuckDB grouping sets like the row subtotals; stepped layout and groups that open and close (`src/lib/analytics/matrix.ts`), set under Table style. Existing pivots keep their layout and look unchanged.
- New Zealand maps (#376 phase 2, decision 687), after Power BI's filled map and map: `filledmap` (one value per region or territorial authority, matched by `areaKey` in `src/lib/analytics/maps.ts`) and `pointmap` (latitude, longitude, optional size). Boundaries are Stats NZ's generalised regional council 2017 and territorial authority 2021 layers (CC BY 4.0, via geoBoundaries), simplified with mapshaper and stored in `src/lib/analytics/maps/`; `src/components/analytics/nz-maps.ts` registers them with ECharts the first time a map is drawn. No map tiles or outside services. Source and changes are in `licenses/nz-boundaries/NOTICE`.
- Non-data items (#376 phase 2, decisions 683-686), after Power BI's text box, image, shapes and buttons: text items with a safe Markdown subset and `{Value}` placeholders (`src/lib/analytics/rich-text.ts` parses to a tree drawn as React elements, never HTML; the values are the item's own ungrouped question), uploaded images stored per report in `analytics_dashboard_images` (tenant migration 0177) and served only to people who can read the report, shapes and lines drawn as SVG in the theme's colours, and buttons whose actions are listed in `BUTTON_ACTIONS` (`src/lib/analytics/items.ts`). Buttons reset to the report's default, go to a page, open a bookmark or go back (decision 759).
- Report pages (#376 phase 3, decision 753) follow Power BI's report pages: `settings.pages` and each tile's `page` (`src/lib/analytics/pages.ts`: `parsePages`, `tilePage`, `tilesOnPage`, `addPage`, `movePage`, `removePage`); the tabs and page settings are `src/components/analytics/report-pages.tsx`. A report without pages is one page and is saved exactly as before.
- Editing a report (#387, decisions 690-691) works on a draft, as in Power BI Desktop: changes show at once in edit mode but only Save or Save and view save them, so report viewers and pinned tiles keep the last saved report. The toolbar says "Unsaved changes" or "All changes saved". Undo and Redo cover this editing session's changes (tiles removed, moved, added or changed, formats pasted, the theme, dates and slicers, the name); they aren't version history and are lost on leaving the page. Leaving with unsaved changes asks first (the browser asks when the tab is closed or reloaded; Tohyee asks for its own links; the browser's Back button isn't covered). Each save names the report version it started from; when someone else has saved since, the save is refused with who and when, and Save mine as a copy or Reload the saved report. A tile added or changed in the draft runs its own question for the preview (bookkeepers and up can run any question); saved tiles run by report and tile, as for report viewers.
- Linear projection (#387, decision 692; it was called Forecast) carries a value's straight-line trend on for 1 to 12 periods after the last date. It extends the trend of the dates shown and nothing else: it isn't Tohyee's cash flow forecast or any forecasting model, and it has no confidence band. It's drawn only when the chart is grouped by a date (day, week, month, quarter or year), oldest first, without Top N, and the answer wasn't cut short, with at least two periods that have a value; otherwise the chart says why it isn't shown. Missing periods between the first and last date are put back on the axis as gaps (no value, never zero) and left out of the fit, and the chart says how many. The projected periods are the grain's next periods, shaded and labelled Projected, drawn dotted with open dots; their tooltips say "(projected)" and "projected, not an actual", and the chart's table for screen readers lists them apart. Charts have no CSV or Excel download of their own; pivot exports have no projections. Saved charts keep the setting (it's still stored as `forecast`).
- Values and joins (#387, decisions 693-696, examples MD1-MD6). Each value in the chart editor has a folded "What <value> means" (what one row is, how it's worked out, unit, movement or balance, date, blanks and zero, totals), worked out from the definition, and "Currency and balances" (the column naming each row's currency; "each row is a balance on its date", for each account or the like). Totals rows work calculated values, averages, smallest, largest and distinct counts out from all the rows. Amounts in more than one currency are left blank where they'd mix, with a note. Tiles read one table; the only join is a shaped table's Merge, which is checked on the data before each preview and rebuild and refused when it would repeat rows or numbers. Shopify and WooCommerce orders reach Analytics only as their invoices and journals.
- Quick calculations (#376 phase 4, decision 770, examples QC1-QC8) follow Power BI's "Show value as" and quick measures: a value's `quick` (`src/lib/analytics/quick-calcs.ts`: `parseQuickCalc` checks it, `describeQuickCalc` says what it's of, `quickTotal` gives the totals row's figure). `buildTileSql` asks the grouped question for every group, then works the calculation out in DuckDB over those groups (windows for runs and ranks, the calendar period before for differences and moving averages, the question asked again for the whole, the first group or the second group for shares, with the exact decimal division), and only then sorts and applies Top N. A pivot's shares are worked out from its cells (`pivotShares` in `dashboards.ts`). The editor's **Show as** is `src/components/analytics/quick-calc-field.tsx`.
- Year, quarter and month to date and the last 12 months (#376 phase 4, decision 771, examples TI1-TI5) follow Power BI's TOTALYTD / SAMEPERIODLASTYEAR: a value's `period` (`src/lib/analytics/time-intelligence.ts`: `parsePeriod`, `periodRange`, `periodStart`, `describePeriod`). With one total or groups that aren't dates, `buildTileSql` gives each value its own dates (its rows are counted with its own From and To, and "and last year" is a second column over `previousYear` of them), reading the rows any value needs. On a chart by date it reads back to the start of the first period's year and adds the groups up within each financial year (`grainSql("fyear")`), quarter or month, or over the 12 calendar months before, then drops the groups before the From date. The editor's **Over** is `PeriodField` in `src/components/analytics/quick-calc-field.tsx`.
- Calculated fields (#376 phase 4, decision 772, examples CF1-CF6) follow Looker Studio's data source fields: `analytics_fields` (tenant migration 0184), `/api/analytics/fields` and `/api/analytics/fields/<id>`, `src/lib/analytics/calculated-fields.ts` (`compileField` type-checks and turns a `parseFieldFormula` tree from `formula.ts` into SQL; `withFields` adds working fields to a table's columns with their SQL as `expression`; `fieldUsage` finds the reports and saved values using one). Queries read `sourceSql(table, columns)`: the table with each field worked out on every row, under the table's own name. The routes that answer tiles, drill-through and slicer values read the fields inside the organisation's transaction and pass them on, so a report viewer's saved tile gets the same fields; `/api/analytics/tables` marks them `calculated: true` without their SQL. The editor's panel is `src/components/analytics/calculated-fields-panel.tsx`.
- What-if parameters and switches (#376 phase 4, decision 773) follow Power BI's what-if and field parameters: `settings.parameters` and a tile's `switches` (`src/lib/analytics/parameters.ts`: `parseParameters`, `parameterValues` and `onStep` check a reader's slider value against the saved steps; `parseSwitches`, `parseChoice` and `applyChoice` turn a reader's positions into the saved tile's question with one value or another saved grouping; `choiceFormat` keeps that value's look). `@name` is a `param` node in value formulas (`formula.ts`), compiled as a decimal parameter from `DashboardFilters.parameters`. The query route applies the choice to the saved tile before anything else, so drill-through, clicks and slicers see the same question. Controls: `src/components/analytics/parameter-controls.tsx`.
- Relationships (#376 phase 4, decision 774, examples RL1-RL5) follow Power BI's many-to-one star model: `analytics_relationships` (tenant migration 0185), `/api/analytics/relationships`, `src/lib/analytics/relationships.ts` (`withRelationships` adds `<name>.<field>` columns, `relatedSourceSql` left-joins each dimension by key, `checkRelationship` reuses `mergeCheckSql` from #399 to refuse a repeated key). `src/lib/analytics/model.ts` reads calculated fields and relationships together (`loadModel`, leaving out farm tables a member can't use) and `questionTables` joins only the relationships a question names, after checking them. `parseBaseMeasure` refuses adding up a related number. The editor's panel is `src/components/analytics/relationships-panel.tsx`.
- Field settings (#376 phase 4, decision 775, examples FS1-FS3) follow Power BI's column properties: `analytics_field_settings` (tenant migration 0185), `PUT /api/analytics/field-settings`, `src/lib/analytics/field-settings.ts` (`parseFieldSettings`, `checkSortBy` on the data, `withFieldSettings` puts them on `ColumnInfo.settings`, which `/api/analytics/tables` lists). `buildTileSql` orders a grouping by `min(<sort column>)` and quick calculations run in that order; a base value's `ResultColumn.number` carries the field's format to `showValue`, `tileChartSpec` and key figures. The editor's panel is `src/components/analytics/field-settings-panel.tsx`; the field list groups by folder.
- Freshness (#387, decision 698). Under a report's dates, each source its tiles read says when it was last refreshed (the last load that finished and was swapped in) and the latest date in the data its tiles go by ("Books and CRM refreshed 21 Oct 2026, 4:05 am, data up to 20 Oct 2026"). When the latest refresh failed, a warning says so and that the report still shows the last good data, which may be out of date; a refresh in progress says it's showing the earlier data. A report on sources refreshed more than an hour apart says the tiles may not agree. No source is ever partly loaded (a database source over its row limit loads nothing; files load whole), so there's no truncated source to show; a tile cut at 5,000 rows says so itself. Report viewers see the same times and dates, without error text. Not built yet from the review's P2 list: links from a tile to its source and value definitions, a preview of what a renamed or removed column breaks, a report-wide limit on running work, and a benchmark.
- Clicks, drill-down and drill-through (#376 phase 3, decisions 754-756) follow Power BI's cross-filter/highlight, edit interactions, drill mode and drill-through. A tile's `drill` (levels) and `interactions` (other tile id → `filter` / `highlight` / `none`) are saved with it. What a reader does is a `view` sent with each tile's question (`src/lib/analytics/report-view.ts`: `parseTileView`, `viewQuery`): the server turns it into a grouping from the tile's own levels and `DashboardFilters.view` filters worked out from the saved tiles, applied like slicers to tiles whose table has the column. Financial years and quarters are the `fyear` and `fquarter` grains (`grainSql` in `query.ts`), named by `periodLabel`.
- Slicer styles, page filters and tile dates (#376 phase 3, decisions 757-758): `src/lib/analytics/slicers.ts` (styles, `rangeFilters`, `slicerOnPage`), `src/lib/analytics/report-filters.ts` (`TileDates`, `effectiveDates`, `PageFilter`), `src/components/analytics/slicer-control.tsx`. Range choices and page filters reach the query as `DashboardFilters.view` filters worked out on the server; a two-level slicer's pairs come from `/api/analytics/values?child=`, scoped to the report's tiles for report viewers.
- Bookmarks (#376 phase 3, decision 759) follow Power BI's bookmarks: `settings.bookmarks` (`src/lib/analytics/bookmarks.ts`), each a page, dates, the report's own slicer choices and hidden tiles. Buttons' `target` names a page or bookmark of the same report (`parseButton`).
- Zoom on time charts (#376 phase 3, decision 760): `format.zoom` adds ECharts `dataZoom` (inside and slider) in `toEChartsOption`. The free-position canvas isn't built.
- Prepare data steps (#376 phase 4, decisions 790-798) follow Power Query's applied steps and its names: Pivot column, Unpivot (and Unpivot other columns), Fill down/up, Replace values, Remove duplicates, Conditional column, Date parts, Sort, Index column and Custom column join the earlier steps (`ShapeStep` in `src/lib/analytics/shaping.ts`; each is parsed by `parseShapeSteps` and built into one DuckDB CTE by `buildShapeQuery`, with every typed value bound as a parameter). The step list and its words are in `src/lib/analytics/shaping-labels.ts`; the forms are `src/components/analytics-shaping-step-form.tsx`, and older steps keep the JSON settings box. Row order: rows keep the order they were loaded in, or of the last Sort, through steps that keep or drop rows; after Group, Pivot, Merge or Append there's no set order, and Fill or Index column then asks for a Sort first. A preview returns `counts` (rows after each step, the base table first) from one query, and `columnsOnly` returns a step's columns without running anything. Custom column reuses the report formula parser (`src/lib/analytics/formula.ts`; never run as code) with exact decimals; Date parts' financial year comes from the organisation's balance date when the preview or rebuild runs. Merges are still checked as in decision 693, and previews stay admin-only.
- Sharing is opened explicitly from the report toolbar. Report viewers stay in viewing mode even with `?edit=1` and do not request source schemas.

Direct Google Sheets and BigQuery connections, a free-position drag-and-drop canvas is not implemented. Google Analytics is connected directly (above); it has been tested against canned Google responses, not a real GA4 property. There is nothing for Looker Studio: Tohyee's own reports are the place to report on these sources. The source picker says which connections are available. Tiles can be a quarter, a third, a half, two-thirds or the full width of a row, and Small, Medium or Large in height (`src/lib/analytics/layout.ts`, decision 596); the report also keeps tile order, dates, slicers, pivots and sharing.

## Who can see what: the access contract (#387, decision 697)

Every figure, row and file Analytics gives out goes through one server-side check of who's asking. Nothing on the page (a slicer, a hidden field, a tile left off, an address like `?edit=1`) is a boundary: the server decides.

| Who | What they can ask for |
| --- | --- |
| Viewers and up (viewer, bookkeeper, admin, owner) | Any question of any loaded table (they can see the tables), every report, slicer values over a whole column. Bookkeepers and up change reports and share them. |
| Report viewers (decision 360) | Only the reports shared with them, and only by report and tile: the tile's saved question, run on the server. Never a typed question, the tables, the sources, the books copy or saved values. |

For a report viewer, every way in uses that same scope (the report, shared with them, and its saved tile):

- **Figures, tooltips and totals.** `POST /api/analytics/query` with `dashboardId` and `tileId` runs the saved tile; a typed `query` is refused (403); an unshared or other organisation's report is "not found" (404). Tooltips, a table's totals row and a key figure's comparison are worked out from that same answer, so they can't show more. Only the report's own slicer fields can narrow the answer; any other filter sent is dropped. The tile's own filters always apply, so choosing a slicer value outside them gives nothing. Dates aren't a boundary: viewers can change them on the page.
- **Detail rows.** A pivot's drill-through (`drill` with `dashboardId` and `tileId`) gives only the pivot's own fields for that cell, under the same filters, up to 500 rows; a hidden column of the table is never in it.
- **Slicer values.** `GET /api/analytics/values` only for a slicer on a report shared with them, and only values in the rows the report's tiles read after their own filters, not the whole column (so a slicer can't name rows the tiles leave out). Tiles on farm tables a member can't use (decision 744) add no values.
- **CSV and Excel.** A pivot's file is made from the figures already on the page (`/api/reports/export`, `analytics-pivot` only, CSV or Excel); the endpoint reads no data itself, so it can't give more than the page.
- **Pinned tiles.** A pin is a report and tile, run through the same query path; once the report is unshared the pin is hidden and its tile returns 404 (decision 378).
- **Related tables** (decision 774) only join tables of the same organisation's analytics copy, many-to-one, checked on the data; a member who can't use a farm table doesn't get relationships to or from it.
- **Parameters and switches** (decision 773). A reader's slider value must be one of the report's saved steps, and a switch is a position in the saved tile's own list; both are checked by the server, and the tile's own filters always apply.
- **Bookmarks and addresses.** A report's address carries only its id and `?edit=1`; report viewers stay in viewing mode and a save from them is refused (403). There are no public links.
- **Calculated fields** (decision 772) read only their own table's columns and are worked out on the server for the saved tile, so they can't reach rows or columns the tile couldn't; report viewers can't list or change them.
- **Caches.** There are none: every answer is worked out for the request.
- **Scheduled outputs.** None exist yet (report emails collect files into Analytics; they don't send reports). When scheduled reports are built, each must run as its recipient, with the recipient's access checked at send time, so an unshared report or a removed member gets nothing on the next run.
- **Email.** Report emails read only the mailbox folder an admin chose for them, run as that admin while they're still an admin, and save attachments (not messages); farm mail stays private to its member (decision 571).

Row-level rules (some report viewers seeing only some rows) aren't built (phase 5 of #376); when they are, they go into this same server-side scope. Tested in `tests/integration/analytics-sharing.test.ts`.

## Database sources: read only

Tohyee only reads from an external database. A typed query must be a single SELECT (or WITH ... SELECT); comments are removed before it's checked and sent, and words that change data (INSERT, UPDATE, DELETE, INTO, EXEC, SET, ...) or functions that write, lock or read the server's files are refused outside quotes. The query then runs inside Tohyee's own outer SELECT, which also applies the row limit; in PostgreSQL the session and each transaction are read only, and in MySQL each read is a `START TRANSACTION READ ONLY` in a read-only session. SQL Server has no read-only session, so the screens ask for a login with read rights only (such as `db_datareader`). Every screen that adds a connection recommends a read-only user.

Connections are made from the Tohyee server, so databases on the local network work. Only admins and owners can add, change, test or see connections. MySQL servers can't ask Tohyee for local files, and a SQL Server that redirects the connection to another server is refused. Connection failures are reported as plain messages (wrong password, no such database, nothing answering, certificate couldn't be checked) without the driver's own text; a query's error shows the database's first line about it.

## Validation

Unit coverage checks connector availability, navigation permissions and forced edit URLs for report viewers. Browser checks against mocked API responses exercise report search/list views, source field inspection, Excel file filtering, load history, live chart editing and saving, report-viewer schema restrictions, and phone-width layouts. These checks do not establish live external service connectivity or database integration; the existing PostgreSQL integration suite requires `TEST_DATABASE_URL`.

Database sources: `tests/integration/analytics-databases.test.ts` connects to a real PostgreSQL (a made-up database and read-only user created and dropped by the test) and checks permissions, saved-password handling, previews, typed-query refusals, the read-only transaction, exact loading into DuckDB, row limits and the nightly reload. MySQL and SQL Server are covered only with stand-in drivers (`tests/unit/analytics-database-drivers.test.ts`), which check what Tohyee sends them, not that a real server accepts it; neither has been tried against a real server yet.
